# GatewayV2 Configuration Contract

**Document version:** 1.2  
**Target:** GatewayV2 V1 firmware + Dashboard V16  
**Status:** Proposed contract to freeze the Dashboard ↔ MCU interface before production implementation  
**Audience:** Embedded firmware, web dashboard, QA/test

### Revision 1.2

- Adds generation-based optimistic concurrency and capability negotiation.
- Defines explicit rejection of unsupported firmware modes.
- Keeps the current firmware configuration body limit at 16 KiB until peak-RAM measurements justify expansion.

- Clarifies the distinction between Modbus **data areas** and Modbus **function codes**.
- Keeps scheduled Data Point polling limited to FC01–FC04.
- Defines the full V1 Modbus TCP ↔ RTU gateway operation set: FC01, FC02, FC03, FC04, FC05, FC06, FC0F, FC10.
- Adds `allow_write` to the Modbus gateway configuration.
- Defines **Read Only** as the recommended default access mode for a new gateway profile.

---

## 1. Purpose

This document defines the configuration and runtime contract between the GatewayV2 web dashboard and the MCU firmware.

The contract has four goals:

1. Keep the Dashboard simple and predictable for installers.
2. Keep firmware memory usage bounded and suitable for an MCU/FreeRTOS implementation.
3. Prevent partial or ambiguous configuration updates.
4. Allow the Dashboard and firmware to evolve independently without silently breaking each other.

The V1 product scope is intentionally limited to:

- Ethernet / Wi-Fi / LTE configuration.
- Three independent RS485 ports.
- Transparent RS485 ↔ TCP Server/Client.
- Modbus RTU Master / data acquisition.
- Modbus TCP ↔ Modbus RTU gateway.
- Modbus data → MQTT publish.
- User-configurable MQTT topic and payload.
- NTP/time settings.
- OTA, reboot, factory reset, backup/restore.

V1 does **not** define BACnet, OPC UA, DNP3, IEC-104, arbitrary scripting, generic protocol conversion, or MQTT-to-Modbus remote control.

## 3. Configuration lifecycle

The firmware MUST treat a configuration POST as one transaction:

```text
HTTP request body
      ↓
parse into staging configuration
      ↓
validate complete configuration
      ↓
reject all OR commit all
      ↓
free parse tree / temporary memory
      ↓
persist to LittleFS
      ↓
notify runtime modules
      ↓
return saved/applied state
```

The firmware MUST NOT partially modify the active runtime configuration while parsing an invalid request.

Recommended implementation:

```text
active_config
staging_config
```

Only after full validation succeeds:

```text
staging_config → active_config
```

### 3.1 Persistent configuration

Recommended storage path:

```text
/configs/config.json
```

Saving SHOULD use a temporary file and rename/replace operation:

```text
config.tmp
   ↓ successful write
config.json
```

A failed save MUST leave the last known valid configuration available.

## 4. Schema version and generation

V1 introduces two root-level metadata fields.

```json
{
  "schema_version": 1,
  "base_generation": 17
}
```

### `schema_version`

- Type: integer
- V1 value: `1`
- Required on POST.
- Returned on GET.
- Unsupported versions MUST return HTTP `422`.

### `generation`

`generation` is generated by the MCU and is not directly editable by the user.

Each successful configuration commit increments it once:

```text
17 → POST valid config → 18
```

`GET /api/config` MUST return the current `generation`.

The Dashboard SHOULD submit that value as `base_generation`.

If the MCU configuration changed after the Dashboard loaded it:

```text
base_generation != current_generation
```

firmware SHOULD reject the POST with HTTP `409 Conflict` instead of overwriting a newer configuration.

## 5. Resource limits — V1

All limits MUST be enforced in both Dashboard and firmware.

These values are the initial V1 limits and may be tuned after heap measurements.

| Resource | V1 limit |
|---|---:|
| RS485 ports | 3 fixed |
| Active service per RS485 port | 1 |
| Serial-over-TCP clients per port | **1** |
| Modbus TCP gateway clients per port | 2 |
| Modbus TCP queued requests per port | 4 |
| Modbus devices total | 16 |
| Data points per device | 16 |
| Data points total | **64** |
| MQTT publishers | 8 |
| Fields per MQTT publisher | 16 |
| MQTT fields total | 64 |
| MQTT topic length | 128 bytes |
| MQTT resolved payload | **2048 bytes** |
| JSON payload template per publisher | 1024 bytes |
| Total JSON template storage | 4096 bytes |
| Data key | 48 bytes |
| Device/profile name | 48 bytes |
| MQTT broker hostname | 128 bytes |
| MQTT Client ID | 64 bytes |
| MQTT username | 64 bytes |
| MQTT password | 128 bytes |
| TCP remote hostname | 128 bytes |
| HTTP `/api/config` request body | **32768 bytes** |

If the HTTP body exceeds the configured maximum, firmware MUST reject it with:

```http
413 Payload Too Large
```

The MCU MUST NOT attempt to parse an oversized body.

{

  }

### 8.1 Interface priority

Accepted V1 values:

```text
eth,wifi,lte
wifi,eth,lte
lte,wifi,eth
```

### 8.2 Static IP rules

If `dhcp == false`:

- `ip` MUST be a valid IPv4 address.
- `netmask` MUST be valid.
- `gateway` MUST be valid or explicitly empty if firmware supports no gateway.

If `dhcp == true`, static fields MAY be retained for future reuse but MUST NOT be applied.

### 8.3 Credential behavior

Passwords MUST NOT be returned in plaintext by `GET /api/config`.

GET example:

```json
{
  "wifi": {
    "ssid": "Factory_AP",
    "password_set": true
  }
}
```

POST behavior:

```text
password field absent     → preserve existing password
password non-empty string → replace password
```

The V1 Dashboard uses this behavior by omitting an empty password field.

The same rule applies to LTE and MQTT credentials.

# 9. RS485 / industrial port configuration

There are exactly three physical RS485 ports.

```json
{
  "modbus": {
    "ports": [
      {
        "enabled": true,
        "mode": "modbus_master",
        "baudrate": 9600,
        "data_bits": 8,
        "parity": 2,
        "stop_bits": 1,
        "tcp": {},
        "modbus": {}
      }
    ]
  }
}
```

The array MUST contain exactly three entries, indexed:

```text
0 = RS485 Port 1
1 = RS485 Port 2
2 = RS485 Port 3
```

## 9.1 Port mode

Accepted values:

```text
disabled       (represented by enabled=false)
tcp_server
tcp_client
modbus_master
modbus_gateway
```

A physical port MUST run only one active service at a time.

The firmware MUST NOT allow simultaneous raw TCP bridging and Modbus Master operation on the same port.

## 9.2 Serial settings

| Field | Allowed values |
|---|---|
| `baudrate` | 9600, 19200, 38400, 57600, 115200 |
| `data_bits` | 7, 8 |
| `parity` | `0=None`, `1=Odd`, `2=Even` |
| `stop_bits` | 1, 2 |

Unsupported combinations MUST return `422`.

# 10. Transparent RS485 ↔ TCP

## 10.1 TCP Server

```json
{
  "mode": "tcp_server",
  "tcp": {
    "listen_port": 4001,
    "max_clients": 1
  }
}
```

V1 MUST limit `max_clients` to **1**.

Reason:

```text
multiple TCP writers → one half-duplex RS485 bus
```

would otherwise require arbitration and request ownership logic that is outside the V1 scope.

Data is byte-transparent:

```text
TCP RX → RS485 TX
RS485 RX → TCP TX
```

The bridge MUST NOT interpret Modbus or modify bytes.

## 10.2 TCP Client

```json
{
  "mode": "tcp_client",
  "tcp": {
    "remote_host": "192.168.1.100",
    "remote_port": 4001,
    "reconnect_ms": 5000
  }
}
```

Validation:

- port: `1..65535`
- reconnect: `1000..60000 ms`
- host: 1..128 chars

# 12. Modbus Data Areas and Polling

A configured **Data Point** represents a value that GatewayV2 reads on a schedule. Therefore the Data Point UI exposes the four standard Modbus read data areas only.

| Read function | Data area | Access characteristic |
|---:|---|---|
| FC01 | Coils | 1-bit, read/write area |
| FC02 | Discrete Inputs | 1-bit, read-only area |
| FC03 | Holding Registers | 16-bit, read/write area |
| FC04 | Input Registers | 16-bit, read-only area |

The write function codes FC05, FC06, FC0F, and FC10 are **operations**, not additional data areas. They MUST NOT appear as Data Point types in the normal polling UI.

The Dashboard MUST nevertheless make the complete V1 Modbus capability visible near Modbus configuration so an installer does not incorrectly conclude that GatewayV2 supports only four function codes. The UI SHOULD group them as:

```text
Read / polling
FC01  Read Coils
FC02  Read Discrete Inputs
FC03  Read Holding Registers
FC04  Read Input Registers

Write / gateway forwarding
FC05  Write Single Coil
FC06  Write Single Register
FC0F  Write Multiple Coils
FC10  Write Multiple Registers
```

The Data Point column SHOULD be labelled **Read Function / Data Area**, not simply `Function`, because it defines scheduled acquisition rather than arbitrary Modbus commands.

Dashboard wording SHOULD be based on the data area, for example:

```text
Coils (FC01)
Discrete Inputs (FC02)
Holding Registers (FC03)
Input Registers (FC04)
```

Canonical point object:

```json
{
  "addr": 0,
  "count": 1,
  "func": 3,
  "type": "uint16",
  "byte_order": 0,
  "multiplier": 0.1,
  "offset": 0,
  "keys": ["meter01.voltage"]
}
```

## 12.1 Address semantics

`addr` is always the **0-based Modbus protocol address**.

Example:

```text
Manual notation: 40001
Protocol address: 0
Function: 03
```

The firmware MUST NOT automatically subtract 40001/30001/etc. The Dashboard is responsible for presenting explanatory UI only; the stored value is always the protocol address.

Range:

```text
0..65535
```

## 12.2 Count and type

For V1, one data-point row represents one logical value.

Recommended required count:

| Data type | `count` |
|---|---:|
| bool | 1 bit |
| int16 / uint16 | 1 register |
| int32 / uint32 / float32 | 2 registers |

The Dashboard SHOULD auto-derive `count` from `type` instead of asking a normal user to choose it.

For FC01/FC02:

```text
type = bool
byte_order ignored
multiplier = 1
offset = 0
```

Dashboard behavior for new/editable rows:

- A newly added Data Point SHOULD default to **FC03 Holding Registers** and `uint16` so the commonly used Data Type, Byte Order, Scale, and Offset controls are immediately editable.
- If FC01 or FC02 is selected, the Dashboard SHOULD visibly indicate that bit-data conversion fields are not applicable instead of making the row appear broken.
- `Count` remains editable within the Modbus function limit. For FC01/FC02 the limit is up to 2000 bits; for FC03/FC04 the protocol limit is up to 125 registers per read request. Product-level limits MAY be lower if required by RAM/timing constraints.
- For FC03/FC04, Data Type, Byte Order, Scale, and Offset MUST be editable.

For V1, arbitrary large raw register blocks SHOULD normally be represented as multiple logical points unless the firmware mapping explicitly supports an array/block value.

## 12.3 Data type

Accepted values:

```text
bool
int16
uint16
int32
uint32
float32
```

## 12.4 Byte order

Accepted values:

```text
0 = ABCD
1 = BADC
2 = CDAB
3 = DCBA
```

Byte order only applies to multi-byte register values.

For 16-bit values, the firmware MAY ignore word-order options that have no effect.

## 12.5 Scaling

Resolved engineering value:

```text
value = decoded_raw × multiplier + offset
```

`multiplier` and `offset` MUST be finite numeric values.

## 12.6 Data key

Each V1 data point MUST contain exactly one logical key in `keys[]`.

Recommended format:

```text
<device_id>.<signal>
```

Example:

```text
meter01.voltage
meter01.current
inverter01.frequency
```

Data keys MUST be globally unique within the active configuration.

Duplicate keys MUST return HTTP `422`.

# 13. Modbus TCP ↔ RTU Gateway

```json
{
  "mode": "modbus_gateway",
  "modbus": {
    "tcp_port": 502,
    "max_clients": 2,
    "gateway_timeout_ms": 1000,
    "gateway_retries": 1,
    "allow_write": false
  }
}
```

V1 rules:

- Modbus TCP `Unit ID` maps directly to RTU slave address.
- TCP Transaction ID MUST be preserved in the response.
- Protocol ID MUST be `0`.
- RTU CRC is generated/verified by the gateway and is not part of the TCP PDU.
- Only one RTU transaction may be active on a physical RS485 port at a time.
- Maximum TCP clients: 2.
- Fixed request queue depth: 4.

## 13.1 Supported gateway operations

GatewayV2 V1 supports the following Modbus function codes in the protocol gateway:

| FC | Operation | Data area | Read/Write |
|---:|---|---|---|
| `0x01` | Read Coils | Coils | Read |
| `0x02` | Read Discrete Inputs | Discrete Inputs | Read |
| `0x03` | Read Holding Registers | Holding Registers | Read |
| `0x04` | Read Input Registers | Input Registers | Read |
| `0x05` | Write Single Coil | Coils | Write |
| `0x06` | Write Single Register | Holding Registers | Write |
| `0x0F` | Write Multiple Coils | Coils | Write |
| `0x10` | Write Multiple Registers | Holding Registers | Write |

This set corresponds to the firmware `MB_Function_t` operation set for GatewayV2 V1.

Read/write function support in the protocol gateway is independent from the `Data Points` UI, which is only for scheduled data acquisition using FC01–FC04.

## 13.2 Gateway access mode

`allow_write` is a boolean gateway policy field:

```text
false → Read Only
true  → Read & Write
```

For a newly created gateway profile, the Dashboard SHOULD default to:

```json
"allow_write": false
```

When `allow_write == false`:

```text
FC01  allowed
FC02  allowed
FC03  allowed
FC04  allowed
FC05  blocked
FC06  blocked
FC0F  blocked
FC10  blocked
```

When `allow_write == true`, all eight V1 gateway function codes are allowed.

The policy check MUST happen before a write request is transmitted onto the RS485 bus. A write request blocked by policy SHOULD be returned to the Modbus TCP client as a Modbus exception response; `0x01` (Illegal Function) is the recommended V1 mapping.

The Dashboard SHOULD label this field as **Access Mode** with two choices:

```text
Read Only (recommended)
Read & Write
```

The Dashboard SHOULD show the supported read/write operations near this setting so the installer can see exactly which commands are permitted.

Timeout without RTU response SHOULD map to an appropriate Modbus gateway exception such as `0x0B` (Gateway Target Device Failed to Respond).

## 13.3 Firmware function-code naming

Recommended firmware naming for the V1 operation set:

```c
typedef enum
{
    MB_FC_READ_COILS                = 0x01,
    MB_FC_READ_DISCRETE_INPUTS      = 0x02,
    MB_FC_READ_HOLDING_REGISTERS    = 0x03,
    MB_FC_READ_INPUT_REGISTERS      = 0x04,
    MB_FC_WRITE_SINGLE_COIL         = 0x05,
    MB_FC_WRITE_SINGLE_REGISTER     = 0x06,
    MB_FC_WRITE_MULTIPLE_COILS      = 0x0F,
    MB_FC_WRITE_MULTIPLE_REGISTERS  = 0x10
} MB_Function_t;
```

This naming is recommended because these enum values represent **Modbus function codes**, not register types.

# 15. MQTT publishers

Example:

```json
{
  "enabled": true,
  "name": "Meter01 Telemetry",
  "topic": "factory/{gateway_id}/{device_id}/telemetry",
  "publish_mode": "periodic",
  "interval_ms": 5000,
  "qos": 1,
  "retain": false,
  "payload": {}
}
```

## 15.1 Topic

Maximum: 128 bytes after template resolution.

Supported V1 variables:

```text
{gateway_id}
{gateway_name}
{device_id}
{slave_id}
{port}
```

MQTT publish topics MUST NOT contain `+` or `#` wildcard characters.

### Context rule

`{device_id}`, `{slave_id}`, and `{port}` are valid only when all Modbus data sources used by that publisher belong to the same source device.

For a publisher combining multiple devices, only gateway-level variables SHOULD be used:

```text
{gateway_id}
{gateway_name}
```

Ambiguous device variables MUST cause validation failure (`422`) rather than silently choosing one device.

## 15.2 Publish mode

Accepted values:

```text
periodic
on_change
periodic_change
```

### `periodic`

Publish every `interval_ms`.

### `on_change`

Publish only after a successful data refresh changes at least one selected source value compared with the last successfully published value set.

V1 defines change as an exact change of the decoded/scaled source value representation. V1 does not define analog deadband/threshold configuration.

For noisy analog signals, the Dashboard SHOULD recommend `periodic`.

### `periodic_change`

Publish immediately when data changes and also publish at least once every `interval_ms`.

`interval_ms` range:

```text
100..3600000 ms
```

## 15.3 QoS

For MCU simplicity, V1 SHOULD support:

```text
0
1
```

Default:

```text
QoS 1
```

QoS 2 SHOULD be hidden/disabled in the V1 Dashboard unless the firmware MQTT implementation has been explicitly verified to support the complete QoS 2 state machine and its RAM impact is accepted.

## 15.4 Retain

Default:

```text
false
```

# 16. MQTT payload contract

Two payload modes are supported.

```text
builder
JSON template
```

## 16.1 Visual builder

```json
{
  "payload": {
    "mode": "builder",
    "fields": [
      {
        "path": "data.voltage",
        "source": "meter01.voltage",
        "type": "number"
      }
    ]
  }
}
```

Field schema:

| Field | Rules |
|---|---|
| `path` | JSON output path, max 64 chars |
| `source` | valid data key or built-in variable |
| `type` | `auto`, `number`, `string`, `boolean` |

V1 built-in sources MAY include:

```text
device.id
device.name
device.gateway_id
modbus.slave_id
modbus.port
system.timestamp
```

All non-built-in source names MUST reference an existing configured Data Key.

## 16.2 JSON template

```json
{
  "payload": {
    "mode": "template",
    "template": "{\n  \"voltage\": {{meter01.voltage}}\n}"
  }
}
```

Maximum template length: 1024 bytes.

Maximum resolved MQTT payload: 2048 bytes.

If payload resolution exceeds the limit, firmware MUST NOT overflow or dynamically expand without bound. It MUST:

1. Abort that publish.
2. Increment an MQTT payload error counter.
3. Preserve the MQTT connection if possible.

No JavaScript, jq, Lua, or arbitrary expression interpreter is part of V1.

# 20. `POST /api/config`

Content type:

```http
Content-Type: application/json
```

Firmware MUST:

1. Enforce body-size limit before parsing.
2. Parse complete JSON.
3. Validate all values and cross-references.
4. Make no runtime changes if validation fails.
5. Persist only after validation succeeds.
6. Increment configuration generation exactly once.
7. Notify affected runtime modules.
8. Return apply state.

Recommended success response:

```json
{
  "status": "ok",
  "generation": 18,
  "saved": true,
  "applied": true,
  "reboot_required": false,
  "warnings": []
}
```

If saved but some settings require reboot:

```json
{
  "status": "ok",
  "generation": 18,
  "saved": true,
  "applied": false,
  "reboot_required": true,
  "warnings": [
    "network.interface_change_requires_reboot"
  ]
}
```

# 21. Validation errors

Recommended error response:

```json
{
  "status": "error",
  "code": "CONFIG_VALIDATION_FAILED",
  "message": "Configuration contains invalid fields",
  "errors": [
    {
      "path": "modbus.devices[0].slave_id",
      "code": "OUT_OF_RANGE",
      "message": "Slave ID must be 1..247"
    }
  ]
}
```

Recommended HTTP mapping:

| HTTP | Meaning |
|---:|---|
| 200 | success |
| 400 | malformed JSON / invalid request syntax |
| 401 | authentication required/failed |
| 409 | stale `base_generation` |
| 413 | body exceeds MCU limit |
| 422 | schema/semantic validation error |
| 500 | persist/internal failure |
| 503 | temporarily busy, e.g. conflicting maintenance operation |

# 22. Cross-field validation

The following checks MUST be performed before commit.

### RS485

- Exactly 3 port entries.
- Modbus device `port` references `modbus_master` port.
- Serial TCP server has exactly 1 client in V1.
- TCP listen ports on the same network stack MUST NOT conflict unless explicit port sharing is supported.
- Modbus Gateway port must not collide with another local TCP service.

### Modbus

- `slave_id` 1..247.
- Data key globally unique.
- Data Point polling accepts only FC01, FC02, FC03, FC04.
- FC01/02 uses boolean type.
- 32-bit types require two registers.
- Point address + required register width must remain within 0..65535.
- `modbus_gateway.allow_write` MUST be boolean when present.
- When `allow_write=false`, FC05, FC06, FC0F and FC10 MUST NOT be forwarded to RTU.
- Unsupported Modbus function codes MUST NOT be forwarded to RTU.

### MQTT

- MQTT enabled requires non-empty broker and client ID.
- Topic after template expansion <= 128 bytes.
- Publish topic contains no `+` or `#`.
- Every payload source exists.
- Publisher using device-level topic variables resolves to exactly one source device.
- Resolved payload MUST fit 2048-byte runtime limit.

### Network

- Static IPv4 fields validated when DHCP disabled.
- At least one configured management-capable network interface SHOULD remain enabled; Dashboard SHOULD warn before applying a config that could remove current management access.

# 27. Authentication contract

All state-changing routes MUST require authentication:

```text
POST /api/config
POST /api/reboot
POST /api/factory_reset
POST /api/firmware_update
POST /api/ota_url
POST /api/ota/abort
```

Production firmware SHOULD also protect:

```text
GET /api/config
```

Basic Auth over plain HTTP protects access control but does **not** encrypt credentials on the wire.

Therefore Web Config over untrusted networks requires an explicit HTTPS/security decision outside this V1 memory budget.

# 28. MCU memory rules

The configuration contract is designed around bounded allocation.

Firmware MUST NOT allow user-controlled counts or lengths to cause unbounded allocations.

Recommended implementation rules:

1. Use compile-time maximum counts.
2. Prefer fixed-size runtime arrays or bounded pools.
3. Parse POST into a staging structure.
4. Avoid making an extra full copy of the HTTP JSON body.
5. Free cJSON/parse structures before serializing the accepted configuration for flash when possible.
6. Do not build static files in RAM; stream LittleFS → HTTP connection.
7. OTA network data → small buffer → flash.
8. MQTT payload generation MUST use a bounded output buffer.
9. TCP/Modbus request queues MUST have fixed capacity.
10. One RS485 port MUST have one service owner.

# 29. Dashboard behavior rules

The Dashboard MUST perform client-side validation for usability, but firmware remains the authority.

The Dashboard MUST:

- Disable Add buttons when resource limits are reached.
- Display usage such as `42 / 64 data points` where useful.
- Preserve existing passwords when password inputs are blank.
- Warn before changing an RS485 port mode if that makes existing Modbus devices inactive.
- Preserve inactive mode configuration where possible instead of deleting it.
- Show Modbus protocol addresses as 0-based values with explanatory text.
- Hide/disable irrelevant fields for Coils/Discrete Inputs.
- Hide periodic interval for `on_change` mode.
- Preview resolved MQTT topic and payload.
- Surface validation errors using the server-provided `path`.

# 30. Recommended changes from Dashboard V14 before schema freeze

V14 is already close to this contract. Three small changes are recommended before production freeze:

### 30.1 Serial TCP max clients

V14 currently permits more than one client in the UI.

V1 SHOULD constrain:

```text
Serial TCP Server → Max Clients = 1
```

### 30.2 MQTT QoS 2

V14 currently displays QoS 2.

V1 SHOULD hide/disable QoS 2 until complete firmware support and RAM impact are verified.

### 30.3 Modbus Count

V14 exposes `Count` as a user-editable field.

For V1 logical Data Points, Count SHOULD be auto-derived:

```text
bool     → 1 bit
16-bit   → 1 register
32-bit   → 2 registers
```

This removes one common user error and simplifies the firmware mapping model.

### 30.4 Stable Modbus device ID

V14 has a human-readable device name but should add a stable machine ID, for example:

```text
ID: meter01
Name: Main Power Meter
```

The stable ID is used by Data Keys and MQTT topic templates.

# 31. Acceptance tests for contract compliance

Before V1 is considered compliant, QA SHOULD verify at least:

1. POST malformed JSON → 400, active config unchanged.
2. POST > 32 KB → 413 before JSON parse.
3. Invalid Slave ID → 422, active config unchanged.
4. Duplicate Data Key → 422.
5. Device references non-Modbus-Master port → 422.
6. Stale generation → 409.
7. Successful POST increments generation exactly once.
8. Password omitted → existing password preserved.
9. GET config never returns plaintext password.
10. 64th Data Point accepted; 65th rejected.
11. 8th publisher accepted; 9th rejected.
12. MQTT topic >128 bytes rejected.
13. MQTT wildcard publish topic rejected.
14. Resolved MQTT payload >2048 bytes fails safely without heap corruption.
15. RS485 TCP bridge rejects/does not configure >1 V1 client.
16. Modbus FC01/02 data point forces boolean semantics.
17. Modbus 32-bit data point uses exactly two registers.
18. OTA streams without allocating image-sized RAM.
19. `min_free` heap decreases during worst-case configuration POST but returns to a stable steady state afterward.
20. Config save interrupted by reset/power loss recovers either the old valid config or the complete new config, never a partially written JSON file.

# 32. V1 freeze summary

The V1 architecture is intentionally simple:

```text
Dashboard
   │
HTTP REST
   │
GatewayV2 MCU
   │
   ├── RS485 raw ↔ TCP
   ├── Modbus RTU ↔ Modbus TCP
   └── Modbus RTU → Data Points → MQTT
```

The core embedded constraint is:

> Every user-configurable collection and string has a hard upper bound.

The core configuration constraint is:

> A configuration update is validated completely, then committed completely, or rejected completely.

The core UX constraint is:

> Guided configuration explains the use case; advanced pages expose the same underlying schema without creating a second configuration model.
